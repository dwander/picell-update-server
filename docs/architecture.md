# 아키텍처 노트

v1(GitHub Releases 프록시)에서 v2(R2 배포 관리 앱)로 바꾸면서 내린 결정과 그 근거.
코드에 안 드러나는 "왜"만 남긴다.

---

## 1. 왜 GitHub Releases를 떠났나

v1은 매 `/update/check`마다 GitHub API를 호출하고 5분 캐시로 버텼다. 문제:

- **레이트 리밋이 곧 장애.** 토큰 없이는 IP당 시간당 60회. 초과하면 403 → 502로
  모든 사용자의 업데이트 검사가 실패했다. 커밋 `839b6c3`(스테일 캐시 폴백)은 이 증상의
  대증요법이었지 원인 제거가 아니었다.
- **릴리즈 노트가 평문 한 덩어리.** 항목 단위로 재사용할 수 없어 요약 배지·누적 변경
  목록·로케일 분리가 전부 불가능했다.
- **배포 제어권 없음.** 단계적 배포, 강제 업데이트, 즉시 철회를 GitHub 릴리즈 플래그
  두 개(prerelease/draft)로 흉내 낼 수 없다.

지금은 릴리즈 메타가 자체 DB, 바이너리가 R2다. 외부 의존이 사라져 캐시·스테일 폴백
로직 자체가 필요 없어졌다. GitHub는 [임포트 도구](../README.md#github-임포트)로만 남았다.

## 2. 왜 버킷을 분리했나 (`picell-one` ≠ `photo-works`)

picell-works-cloud는 `photo-works` 버킷을 쓰고, 그 프로젝트의 고아 객체 정리 도구
(`packages/core/orphan-storage.ts`)는 **버킷 전체를 리스팅해** DB가 참조하지 않는 키를
삭제 후보로 올린다. 그쪽 분류기가 모르는 키 형태는 "기타"로 떨어진다.

같은 버킷에 업데이트 바이너리를 두면 언젠가 그 스캔이 우리 파일을 후보로 집어낸다.
버킷을 분리하면 이 위험이 구조적으로 사라진다. 반대로 우리 쪽 정리 도구
(`services/storage-admin.ts`)도 삭제 범위를 `releases/` 프리픽스 안으로만 제한한다 —
나중에 `picell-one`에 다른 용도가 생겨도 오삭제가 나지 않도록.

## 3. 업로드 경로: presigned PUT 직결

브라우저 → R2 직결이 기본이다. 서버를 통과시키면:

- Railway 요청 크기 제한에 걸린다.
- 100MB+ 바이너리가 Node 프로세스 메모리에 올라간다.
- 업로드 중 서버 재배포가 일어나면 통째로 날아간다.

서버는 키 발급과 **완료 검증**만 맡는다. 완료 처리(`services/artifacts.ts`)는 R2에
HEAD를 날려 객체가 실제로 도착했는지 확인하고, 되읽어 `sha256`을 계산한다.

> **왜 브라우저에서 해시를 받지 않나:** 클라이언트 계산값은 신뢰 근거가 없고,
> 대용량 파일을 브라우저 메모리에 통째로 올려야 한다. R2→서버 스트리밍은 같은
> Cloudflare 망 안이라 비용이 사실상 없다.

두 번째 경로인 **URL 임포트**는 서버가 원본을 스트리밍으로 받아 멀티파트로 올린다.
GitHub 이관이 이 경로를 그대로 쓴다.

### CORS는 필수이고, 빠뜨리면 조용히 실패한다

presigned PUT은 브라우저에서 나가므로 버킷에 CORS 규칙이 없으면 업로드가 실패한다.
**이 실패는 서버 로그에 남지 않는다** — 브라우저 단계에서 끝나기 때문이다.
`infra/r2-cors.json` 참고. 콘솔은 이 경우를 대비해 XHR 오류 메시지에 CORS를 명시한다.

## 4. 체인지로그를 구조화한 이유

`changelog_items`(타입 + 텍스트 + 순서)를 1차 데이터로 두고 마크다운은 파생물로 만든다.
단, **직접 쓴 마크다운이 있으면 그쪽이 우선**한다 — 편집기에서 모드를 오가도 데이터가
사라지지 않게 하는 유일한 규칙이다(별도 모드 플래그를 두지 않는다).

구조화의 대가로 얻는 것:
- 클라이언트가 `items`를 받아 타입별 아이콘·색으로 렌더할 수 있다.
- `/update/changelog?since=`로 여러 버전의 변경점을 합쳐 보여줄 수 있다.
- 한국어/영문을 같은 항목 구조로 따로 관리할 수 있다.

## 5. 단계적 배포는 왜 결정론적이어야 하나

`isInRollout()`은 `sha256(machineId + version)`의 상위 32비트를 100으로 나눈 나머지로
판정한다. 요청마다 난수를 쓰면 같은 PC에서 업데이트 알림이 **보였다 사라졌다** 한다.

버전을 해시에 섞는 이유: 버전마다 대상 집합이 달라져야 특정 PC가 매 릴리즈 초기
배포에서 계속 제외되거나 계속 포함되는 편향이 생기지 않는다.

`machineId`가 없으면 결정론적 판정이 불가능하므로 **100% 배포일 때만** 포함한다.
업데이트가 깜빡이는 것보다 보수적인 쪽이 낫다.

## 6. 설치 기반 통계(`installs`)와 활동 로그(`check_log`)

다운로드 수만으로는 "지금 어떤 버전이 실제로 돌고 있는지" 알 수 없다 — 설치 후 롤백,
재설치, 여러 번 받고 안 쓴 경우가 전부 섞인다.

`/update/check`가 `machineId`를 주면 두 곳에 남긴다. 역할이 다르다:

| 테이블 | 형태 | 답하는 질문 |
|--------|------|-------------|
| `installs` | machineId당 1행 (덮어쓰기) | **지금** 어떤 버전이 돌고 있나 |
| `check_log` | (날짜 × machineId)당 1행 (영구) | **언제** 살아 있었나 |

스냅샷만으로는 활성 사용자 추이를 낼 수 없다 — `installs`는 확인이 올 때마다
`last_seen_at`을 덮어써서 과거가 사라지고, 남는 건 "최근 N일 안에 확인한 대수" 하나뿐이다.
그래서 시간축을 따로 남긴다.

**왜 요청마다 한 행이 아닌가.** 클라이언트 확인 주기(현재 앱은 몇 시간에 한 번)가 그대로
행 수가 되면, 주기를 바꾸는 순간 로그 크기가 몇 배로 뛴다. 활성 사용자 판정에 필요한 건
"그날 살아 있었나"뿐이므로 하루치를 한 행으로 접는다. 그러면 행 수가
**설치 대수 × 운영 일수**로 묶여 확인 주기와 무관해지고, 영구 보존해도 SQLite가 감당한다.
하루 안의 정보는 잃지 않는다 — 확인 횟수는 `checks`에 누적하고, `version`은 그날 마지막
보고값을 남긴다(하루 안에 업데이트가 끝나면 그 결과가 보인다).

**감사 로그와 달리 잘라내지 않는다.** `audit_logs`는 최근 2000행만 남기지만
활동 로그는 과거를 지우는 순간 추이 자체가 사라진다. 크기는 위 형태로 이미 묶여 있다.

날짜 키는 UTC(`YYYY-MM-DD`)다. 기존 일별 다운로드 집계가 `date(…, 'unixepoch')`로 UTC를
쓰고 있어, 두 차트를 나란히 놓았을 때 하루가 어긋나지 않으려면 기준이 같아야 한다.

이 집계 실패는 업데이트 확인을 막지 않는다(try/catch로 삼킨다).

## 7. 인증: Basic Auth → 세션 쿠키

v1은 `/stats`에 Basic Auth를 걸었다. SPA에서는 두 가지가 문제다:
로그아웃이 불가능하고, 모든 XHR에 자격증명이 실려 나간다.

지금은 `ADMIN_PASSWORD` 검증 후 랜덤 토큰을 httpOnly 쿠키로 발급하고, **토큰 해시만**
DB에 저장한다(DB가 새더라도 세션 탈취 불가). 비밀번호 비교는 해시끼리 `timingSafeEqual`.

`STATS_PASSWORD`를 `ADMIN_PASSWORD`의 폴백으로 인식하므로 기존 배포가 잠기지 않는다.

## 8. SQLite를 유지한 이유와 그 대가

관리자 한 명이 쓰는 단일 인스턴스라 Postgres를 붙일 이유가 없다. 부팅 시
`db/migrate.ts`가 멱등하게 스키마를 맞추므로 마이그레이션 파일 체계도 불필요하다.

**대가:** 릴리즈 메타가 이 파일에만 있다. `DB_PATH`를 **Railway 볼륨 경로**로 지정하지
않으면 재배포 때마다 전부 사라진다. R2의 바이너리는 남지만 어떤 릴리즈였는지는 모른다
(스토리지 화면에서 고아로 보인다). 볼륨 설정은 선택이 아니라 필수다.

## 9. 남은 것

- **릴리즈 매니페스트 R2 미러링** — DB 유실 시 R2만으로 릴리즈 메타를 복구할 수 있게
  `releases/{version}/manifest.json`을 함께 쓰는 안. 볼륨을 제대로 걸면 우선순위는 낮다.
- **델타 업데이트** — `blockmap` kind는 스키마에 자리만 잡아뒀고 로직은 없다.
- **코드 서명 검증** — 현재는 `sha256`만 제공한다. 서명 검증은 클라이언트 몫.
